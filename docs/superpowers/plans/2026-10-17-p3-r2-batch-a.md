# P3 批次一 R2-A（桶控制面 + 对象 REST 闭环）实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 让 R2 从只读目录升级为可操作产品：桶的建立／读取／修改／删除闭环，以及对象 REST 的列出／下载／上传／删除闭环（共 10 个 operationId）。

**Architecture:** 沿用 P1／P2 已稳定的四层——`model`（文档与输入，保留 unknown ）、`ports`（typed 端口 + `beforeSend` 守卫的 session）、`application/r2`（校验与 controller）、`cloudflare/r2`（typed 客户端）。对象内容只经 P1 `TransferPort` 流式通过，不进 core 内存。写动作走 P1 `ChangePlans`／`OperationCoordinator`，不新增确认机制。

**Tech Stack:** Kotlin Multiplatform（commonMain）／kotlinx.serialization JsonObject／OkHttp 传输层／SQLDelight 任务存储／Compose（shared-ui）／Android SAF（android-platform）。

**Spec:** `docs/superpowers/specs/2026-10-17-p3-r2-management.md`（实施前需用户批准）。

## Global Constraints

- 固定 schema 来源：`.superpowers/cloudflare/openapi.json`（commit `6b00f157496cd6a1792a613dc94654c51273aeb9`）。每个 operationId 的 method／path／参数以该文件为准，不凭记忆或网页摘要实现。
- 桶名：`minLength=3`、`maxLength=64`、pattern `^[a-z0-9][a-z0-9-]*[a-z0-9]`（`r2_bucket_name`）；追加拒绝 IPv4 形式、`xn--` 前缀、`-s3alias` 后缀。
- 对象 key：非空、UTF-8 ≤1024 字节、无 C0／C1 控制符与 `\`、不是 `.`／`..`、不以 `/` 开头；**路径中斜杠字面发送，不编码成 `%2F`**（官方 `object_key` 参数说明：slashes 字面发送，其余保留字符照常百分号编码）。
- 枚举写入只允许：`locationHint ∈ {apac, eeur, enam, weur, wnam, oc}`、`storageClass ∈ {Standard, InfrequentAccess}`；未知值读取保留、写入拒绝。`cf-r2-jurisdiction` 头（`default`／`eu`／`us`／`fedramp`／`fedramp-high`）随 R2-B 的 jurisdictions 支持一起接入，本批不用。
- 批量删除 1–1000 个 key；已弃用的 `prefix` 参数不暴露。`r2-create-temp-access-credentials` 不在本批（需单独批准）。
- 对象内容不得进入 core 内存、日志或剪贴板；只用 `ByteSource`／`ByteSink`／`TransferPort`。
- 真实云资格保持 0；本批不做真实云写入。
- 提交只包含本任务列出的文件，不使用 `git add .`；不创建 Tag／Release；不推送合并除非用户授权。

## Review Focus

1. 对象 key 的斜杠、空格、`+`、非 ASCII、前导 `/`、`.`／`..`、超 1024 字节：合法 key 必须原样到达（斜杠不编码），非法 key 发送 0 次（Task 1、4）。
2. 4 MiB 以上对象下载不得走内存 bounded 路径，上传不得整体读入内存，取消后 sink／source 都关闭且不留半成品（Task 4、5）。
3. 1001 个 key 的批量删除：发送 0 次且错误可解释；响应缺失或矛盾时 UNKNOWN 且只回读不重发（Task 5）。
4. 删除非空桶／存在 multipart／存在通知规则：provider 失败映射为可解释前置条件错误，不重试、不误报成功（Task 3）。
5. `r2.dev` 公共访问启停与自定义域删除：需明确确认，权限不足时拒绝写入而非静默失败（Task 3、6）。

**Follow-up（本批不修，已用测试钉住现状）：**

1. 共享 `requestShapeIsSafe` 的多级解码会把字面 `%` 后面跟两个十六进制字形的 key（例如 `a%25bc`）判为非法 UTF-8 而拒绝。
2. 共享校验器拒绝**任何解码后含 `#` 的路径**，因此 key 里带 `#`（如 `report#1.csv`）会被拒。我们的编码本身是对的（`report%231.csv`），但共享校验器把解码后的 `#` 当成片段分隔符。拒绝是安全结果，但能力上确实缺失。

- [ ] **Step 3：实现端口与客户端**

## Task 5：对象上传、单删与批量删除

**接口修正（按 pinned schema）：**

1. `deleteObjects` 不接受 `R2ObjectTarget`（批量端点寻址集合，没有单个 key），而是 `(account, bucket, keys)`。
2. **`r2-delete-objects` 不是原子的**：官方说明中任一个 key 失败时 `success=false`、`result=null`、`errors` 每个失败 key 一条，**其余 key 仍然已删除**。所以 `R2BulkDeleteOutcome` 需要 `confirmedDeleted` + `failedCount` + `uncertain` 三个字段，部分结果必须标 `uncertain=true` 且只回读不重发。

## Task 5b：`R2Controller`（桶生命周期的预览、确认与对账）

**状态：** 桶部分已完成；**对象写入（upload／delete／bulk delete）的控制器尚未接线**（`R2ObjectWrite` 已经能走 `R2ObjectSession.writeObject`，但还没有 prepare／confirm 封装）。

**设计：**复用 P1 `ChangePlans` + `OperationCoordinator`，不新造第二套确认。资源锁按**桶**粒度（`ResourceRef(scope, "r2_bucket", name)`），所以桶删除不会与同一个桶的编辑并发。

**关键决定：**

1. **删除必须输入桶名**。`R2BucketWrite.Delete(scope, name, typedName)`，`name != typedName` 直接拒，且在任何读之前就拒。
2. **创建时的"不存在"只能用 404 证明。**桶列表的 `result_info` 没有 `total_count`，分页不完整不能当作不存在；所以 `requireAbsent` 用 `getBucket` + 只接受 `NOT_FOUND`，其余失败原样抛出。
3. **写入前的冻结比对。**`prepare` 记下 `beforeHash`；`submit` 在最后一道 guard 里重新读并比对，不一致就抛 CONFLICT，**发送次数 0**。
4. **对账只读。**delete 读到 `NOT_FOUND` 才 Matched；patch 只在 `storage_class` 真的等于 desired 时才 Matched；其余一律 `StillUnknown`，不重发。

**接线时必须知道的一个共享行为（实测确认，不是推测）：** `OperationCoordinator.runConfirmed` 会捕获 `write(beforeSend)` 抛出的**任何**异常并返回 `RUNNING` 任务，不向调用方重抛——因为它无法区分"发送前就停了"与"发送后失败"。所以上面第 3 条的最终 guard 冲突表现为：**确实一次都没发**（`sends == 0`），但调用方拿到的是一个需要核对的 `RUNNING` 任务，而不是一个干净的 CONFLICT 错误。`R2ControllerTest.aBucketChangedBetweenPrepareAndSubmitBlocksTheSend` 把这个行为钉住了（Zone 控制器一致）。UI 层不能把这种情况渲染成"失败，请重试"。

## Task 5c：对象写入的控制器接线

**状态：** 已完成。

**模型变更：**
- `R2ObjectWrite.Upload` 新增必需的 `contentFingerprint`（平台暂存时流式算出的 SHA-256）。它进入 request fingerprint，所以**预览后文件内容变了就不能用旧批准上传**。没有它就只能绑定 target 与大小，等于漏掉“输入变化”这类绑定。
- `R2ObjectWrite.Delete` 新增 `typedKey`（必须等于 key）。
- 新增 `R2Session : R2ManagementSession, R2ObjectSession`，控制器只需一个凭据绑定对象。

**两处一定要知道的接口后果：**

1. **`uploadObject` 因此多一个参数**（content fingerprint），`CloudflareR2Client` 与平台暂存层必须一起改；将来接 SAF 时，哈希要与“暂存副本”同时产出，不能写完再读一遍。
2. `R2ObjectWrite.Delete` 的 `typedKey` 已接入，但客户端 `deleteObject` 这类信任传输口直接传 `key == typedKey`；真正的输入确认在控制器。

**对象任务的安全定位：**沿用 DNS 逐记录任务的形状——`ResourceRef(scope, "r2_object", "<bucket>/<key>")`，批量删除用 `"<bucket>/"`（空 key 表示桶内集合）。因此：

- 资源锁是**逐对象**的（与 DNS 逐记录一致），另外用 `anyUnsettledForBucket` 把同一个桶的所有 R2 写入互相阻断；
- 外部标识里第一个 `/` 之前是桶名（桶名不允许 `/`），所以拆分不会有歧义；
- **不得把对象 key 放进 `pollPath`**——那不是它的语义。第一版曾这么写，已改正。

**对账边界：**

- 对象是否存在，靠**穷尽该 key 前缀的列表**判定（R2 强一致）；达到页面上限就报错而不是回答，因为不完整的列表不能证明不存在。
- 上传对账要求该 key 真的出现在列表里；删除对账要求穷尽后确实缺席。
- **批量删除对账返回 `ActionRequired`**：证明最多 1000 个 key 真的消失需要逐 key 回读，App 做不到；与其假装成功，不如让用户去官方控制台核对。
- 哈希比较的坑：`objectDesired` 含 `bucket` 字段，对账候选也必须带 `bucket`，否则永远不 Matched（已用测试钉住）。
